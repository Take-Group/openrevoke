# Click recipes: writes in apps without an API

Decided 25.11.2026.

## Decision

Order of paths for each app:

1. Official API with a token or OAuth, when it can create and delete accounts.
2. SCIM, when the customer has a plan with SCIM (usually Enterprise). The
   `scim` connector stays, but it is not a priority.
3. Browser with an admin session:
   - **read** the account list through `fetch()` in the panel tab (fast,
     every 6 hours during sync, an error breaks nothing),
   - **write** (invite, delete, deactivate) through a **click recipe**:
     steps in the admin panel, the way a person does them.
4. A task for a person, when no recipe exists or the recipe cannot be
   repaired.

Why write by clicking and not by request: a click fails loudly (the button
is missing, the step stops), while a request to a private API can return
200 and do nothing. Layout changes happen more often, so a recipe must be
able to repair itself.

The pattern from the market that we adopt: AI builds and repairs the
recipe, and a deterministic engine without a language model runs it. The
open source tools Skyvern and Stagehand do the same. AI does not click live
at every step.

## Recipe format

A recipe is a JSON file, not code. The Open Revoke engine runs it, so a
recipe cannot run anything beyond the steps below. Such a file can be
reviewed, compared with a diff, signed and shared between installations.

```json
{
  "app": "browser_fake",
  "version": 1,
  "actions": {
    "delete_account": [
      {"id": "open-users", "do": "goto", "url": "{{panel_url}}/admin"},
      {"id": "open-row-menu", "do": "click", "goal": "Open the actions menu of the user",
       "within": {"role": "row", "has_text": "{{email}}"},
       "target": [{"css": "[aria-haspopup=menu]"}, {"role": "button", "name": ["Actions", "Akcje"]}]},
      {"id": "choose-remove", "do": "click", "goal": "Choose removal in the menu",
       "target": [{"test_id": "remove-user"}, {"role": "menuitem", "name": ["Remove", "Usuń"]}]},
      {"id": "check-confirmation", "do": "expect", "goal": "The confirmation names the user",
       "target": [{"role": "dialog"}], "text": "{{email}}"},
      {"id": "confirm-remove", "do": "click", "goal": "Confirm the removal", "irreversible": true,
       "within": {"role": "dialog"},
       "target": [{"css": "#confirm-ok"}, {"role": "button", "name": ["Remove", "Usuń"]}]}
    ]
  }
}
```

Steps:

| `do` | What it does |
|---|---|
| `goto` | opens `url` in the recipe tab |
| `click` | clicks the `target` element |
| `fill` | types `value` into the `target` field |
| `press` | presses the `value` key (e.g. `Enter`) in `target` or, without `target`, in the active element |
| `expect` | checks that `target` is visible and contains `text` |

The step `id` is fixed and unique within the action. Local fixes are
pinned to it (section "Local fixes and releases").

`{{...}}` parameters: `email`, `external_id`, `name`, `first_name`,
`last_name`, `role` from the action, and the fields of the connection
config (e.g. `panel_url`). A missing parameter is an error before the first
step.

## How a recipe points to an element

- `target` is a list of candidates in order. The first candidate that gives
  **exactly one** visible element wins. Zero or more than one: next
  candidate. None: the step fails.
- Order of candidates: first the **language-independent** anchors, then
  text. Independent: `test_id` (`data-testid`), `css` on a stable
  attribute (`data-qa`, `id`, field `name`, `type="email"`,
  `aria-haspopup`, `href` with the user ID), `role` without `name`.
  Language-dependent: `role` with `name` (a list of exact names in several
  languages), `label`, `text`. Never CSS classes generated by frameworks
  (random hashes) and never position ("the last button").
- `within` narrows the search to one container, e.g. the table row with the
  person's e-mail. The container must also be exactly one. This way the
  recipe clicks the button in the row of the right person, not the first
  button on the page.
- The engine waits up to 10 s for an element (pages load by script).
- `goal` says in English what the step must achieve. The AI reads it during
  repair, and a person reads it in an error.

## Safety

- An `irreversible` step (confirmation of a deletion) needs an earlier
  `expect` step whose `text` contains `{{email}}` or `{{external_id}}`.
  A recipe without it is rejected at load.
- An irreversible step is never repaired automatically. An admin approves
  the new element.
- A recipe runs in a **separate tab**, closed after the run. It does not
  disturb the panel tab that the `fetch()` read uses, or the admin. Cookies
  are shared, so the admin session works.
- A write runs under the connection lock, like every write (`skills/backend/actions.md`).
- A read-back verification always follows a recipe. A recipe that passed
  all steps while the account still exists ends the action as `failed`.

## When a recipe breaks

1. **Detection.** A step did not find the element, found several, an
   `expect` does not match, or the read after the action shows no change.
   The error says which step, which `goal`, and what each candidate found.
2. **Repair by AI** (built: `services/recipe_repair.py`). The model from the AI settings gets the `goal`
   of the step, the accessibility tree of the page and a screenshot, and
   proposes a new candidate. The engine fixes a navigation step and an
   `expect` step by itself and goes on. An irreversible click waits for the
   admin's approval: "instead of X I will click Y".
3. **Local fix.** The repair saves the new candidate for the step `id`
   on this installation, with the author (AI or admin) and the date. It can
   be undone.
4. **Person.** When the AI does not find the element, the action ends as
   `failed` with a screenshot of the place where the recipe stopped. The
   admin picks "Retry" (read first, write only if the change is not there
   yet) or "Do it by hand" (the action becomes a manual task).
5. **Early warning.** The sync every 6 h goes through the panel. A broken
   read shows up before the offboarding day.

## Panel language

Button names usually depend on the language set on the admin account, not
on the browser. Therefore:

- a recipe starts with language-independent candidates (above),
- `name` is a list of names in several languages,
- Chromium starts with `--lang=en-US`; this helps in apps that take the
  language from the browser,
- when an app is connected, the panel **recommends** an English admin
  interface, and best of all a separate integration account (an admin only
  for Open Revoke) with an English interface. A recommendation, not a
  requirement,
- the rest is repair by AI: the agent searches by `goal`, so it finds the
  button in any language, and the fix stays local.

## Where recipes live

- In the MVP, next to the connector: `backend/app/connectors/<key>/recipe.json`.
- Recipes of apps sold in the catalog will go to `ee/` (license
  `ee/LICENSE`). The engine and the format stay MIT.
- Fixes from installations: in the database, rules below.

## Local fixes and releases

Rule: a fix made at the customer's installation (by their AI or
admin) takes precedence over the recipe from a new release. We merge them
per step, not by replacing the whole recipe:

- A local fix is a candidate pinned to the step `id`. At run time the local
  candidates go first, then the candidates from the repo. The customer's
  fix wins, and the fix from a new release works as a fallback when the
  local one stops matching.
- The list of steps, their order, `expect` and `irreversible` always come
  from the repo. Locally you cannot remove a step or bypass the e-mail
  check.
- A release that removes or changes a step `id` invalidates the local
  candidates of that step; the panel shows them as outdated.
- The engine records which candidate worked. A local candidate that stopped
  working while a candidate from the repo worked is marked as outdated.

## What we do not use

- Skyvern: AGPL license, while the core is MIT.
- browser-use workflow-use: the README says that the fallback to an LLM
  after an error is "currently really bad".
- Code generated by AI and run on the server: a recipe is data, not
  code.
